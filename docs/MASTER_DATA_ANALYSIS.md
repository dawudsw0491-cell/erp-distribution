# Master Data Analysis — AS-IS and TO-BE

**Baseline:** commit `8eadef2`, 2026-11-19

## AS-IS inventory

| Entity / capability | Existing route or implementation | Current responsibility | Assessment |
|---|---|---|---|
| Product | `/products` | Product identity, SKU, category, brand, type, condition, tracking | Core entry point |
| Product Variant | `/products/[id]/variants` | Transaction/inventory variant, barcode, unit | Keep nested under Product; Inventory depends on variant ID |
| Product Category | `/product-categories` | Category and parent/child classification | Separate reference CRUD is appropriate |
| Brand | No dedicated route; create actions embedded in Product and Product Model | Brand reference | Duplicate creation entry points; centralize after schema/UX review |
| Product Model | `/product-models` | Model-level grouping/metadata | Existing route; relation to Product and attributes needs canonical mapping |
| Product Attributes | `/product-attributes` | Attribute definitions, data type, unit, category applicability | Separate dictionary is appropriate |
| Product Attribute Values | `/product-attribute-values` | Values linked to variant/attribute in current SQL | Relationship differs from model assignment usage in application code |
| Supplier | `/suppliers` | Supplier identity, contacts, bank accounts, product relations | Keep as partner master |
| Customer | `/customers` | Customer identity and regional/address data | Keep as partner master |
| Warehouse | `/warehouses` | Physical stock location | Operationally belongs to Inventory; Purchasing consumes it |

## Main design principles

1. Product `id` is the stable internal product identity.
2. Product SKU is generated by the database RPC `generate_product_sku`; do not introduce a competing generator.
3. Product variants remain intact because inventory balances, movements, units, goods receipt, and serialized tracking depend on variant IDs in the inspected source.
4. Category, brand, attribute definition, supplier, customer, and warehouse are reference entities; do not duplicate their records inside product forms.
5. Condition (BARU/SECOND), type (GOODS/SERVICE), and tracking (QUANTITY/IMEI/SERIAL) remain product classification dimensions. Do not replace or rename them without a migration and full usage analysis.
6. Attribute definitions are dictionaries; attribute values are assigned data. The exact assignment grain (model, product, or variant) must be settled from actual DB schema before consolidation.
7. Warehouse remains a single master entity consumed by Inventory and Purchasing; do not create a second warehouse table.

## TO-BE navigation and responsibility

- Master Data Hub is the central entry point.
- Hub cards link to existing CRUD routes; the hub does not duplicate CRUD forms.
- Product Variants remain accessed from Product detail.
- Brand should eventually have one canonical management path; current creation helpers are duplicated.
- Product Model and Product Attribute routes remain distinct until their schema relationships are verified.
- Supplier, Customer, and Warehouse remain separate data-management pages, reachable through the Master Data area and existing routes.

## Implementation completed in this baseline

Master Data Hub now exposes all eight existing top-level Master Data work areas:
Product, Category, Customer, Supplier, Warehouse, Product Models, Product Attributes, and Product Attribute Values.

No database table, function, trigger, policy, Inventory logic, or existing CRUD route was changed.

## Deferred decisions

- Whether Product Model is a catalog classification or an identity layer for product records.
- Whether attribute values should be attached to product model, product, or product variant.
- Whether the legacy `product_variant_attribute_values` table is still required.
- Whether Brand should be a dedicated page or a shared section in a consolidated catalog screen.
- Whether product variants are commercially distinct SKU records or inventory-only options in every product category.

These decisions require schema introspection and representative data review, not assumptions from page names.
